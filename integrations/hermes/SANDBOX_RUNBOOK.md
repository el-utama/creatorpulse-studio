# Sandbox installation and recovery — agent execution runbook

This is the canonical task for Hermes on the Windows host. Read [AGENTS.md](../../AGENTS.md) first. **Execute, verify and resume**; do not ask the owner to relay individual commands. Treat all host-specific paths below as hints, not proof. Use the matching branch sandbox; never deploy main, change production, or post content.

Known retired Sandbox private paths are probed without reading any bytes. The owner helper inventories and, with explicit PROTECT approval only for retired Sandbox copies, normalizes ACLs on those exact paths; no content deletion, Production changes, or unrelated ACL edits. If unscoped old files are still in use or cannot be identified, decline protection and report the blocker. The controller checks effective old-path access again before gateway or MCP activation. This does not establish isolation of arbitrary copies elsewhere.

For existing PC09 recovery, the executable controller `python integrations/hermes/windows_resume.py` is authoritative; its JSON state replaces agent interpretation of the gates below. Use the existing Hermes Python and clean, freshly fetched sandbox checkout. Do not run individual steps if the controller reports a blocker. Owner isolation review is recorded as an attestation, not independent proof. The controller verifies the receipt ACL before using the exported credentials, checks gateway enrollment before applying MCP, and validates the installed adapter via read-only JSON-RPC plus the supported Hermes CLI test.

- Identify the current Windows user, OS, clean checkout/commit, Python installations available to that identity, Hermes version and profile list. Never dump .env, config contents, process command lines, credentials or chat memory. Use metadata and targeted checks.
- Run `powershell -NoProfile -File integrations/hermes/windows-preflight.ps1` from the checkout. It reports service-account existence, port 8766, named task status, safe paths and dedicated profile presence; access denied means unknown, not absent.
- Existing installation hints: PC09-PR, user USER, dedicated account CreatorPulseBridge, old checkout C:\Users\USER\CreatorPulseBridge, protected service root C:\ProgramData\CreatorPulseBridge, dedicated profile creatorpulse-sandbox under %LOCALAPPDATA%\hermes\profiles or the installed Hermes home. Sandbox Bridge 127.0.0.1:8766, existing Funnel HTTPS port 10000. Vercel canonical host https://creatorpulse-studio-git-sandbox-total-management1.vercel.app. An earlier live test returned HTTP 200 before migration; reverify after migration. Do not assume any gate passed on the present host.
- If a dedicated profile exists, reuse it, never clone default credentials. Otherwise inspect CLI help and create clean profile using --no-credentials --no-alias. Configure only owner-approved NVIDIA NIM settings in that profile; preserve default, messaging, schedules and all other profiles. Owner supplies provider credentials locally if missing.
- Run repository Python tests with an available interpreter, without installing anything into default Hermes. Dry-run bootstrap with the actual Hermes Python/PyYAML and explicit dedicated profile. Do not run setup.py merely because access to protected files is denied.

## 2. Bridge provisioning or recovery (owner boundary)
Agent: inspect metadata, prepare installation and a single owner approval bundle; never enter the private service directory, read owner secrets, access Vercel CLI login, impersonate the service account or bypass UAC. If owner setup is already successful, skip this gate.
Owner: review the script and repository revision independently of agent-writable files. For fresh installations follow [Local Bridge](../../local-bridge/README.md) for setup.py and distinct Sandbox credentials. Only the owner generates credentials, sets branch-scoped Vercel variables, and configures HTTPS. Never regenerate credentials on recovery.
For existing Windows migration:
1. Stop only the old Bridge listener gracefully; never kill an unidentified process. Ensure SQLite WAL is checkpointed or use a complete consistent backup. Preserve old data until validation. Do not overwrite an existing protected database or key.
2. Use dedicated non-admin Windows account CreatorPulseBridge, protect the service directory and every child (SYSTEM, Administrators, service identity only; trusted owner, no agent ownership). Check effective access as non-elevated agent; if it can elevate without owner approval this is not isolation. Transfer existing code, DB and private configuration without logging values. If already migrated, verify; do not recopy.
3. If Python launcher is absent under the service account, obtain a supported Python 3.10+ Windows x64 embeddable ZIP from python.org and independently verify its SHA256 against trusted release information. No modification of existing Python/PATH. For the already migrated host use [windows-owner-start.ps1](windows-owner-start.ps1) without arguments: it downloads pinned official Python 3.13.17 x64 into the protected root, verifies the published SHA256 and executable signature, and checks sqlite3/ssl imports. Only for an alternate verified runtime supply -PythonArchive and -PythonSha256. The helper is specific to the current PC09 migration and checks the existing PC09 HTTPS route. With explicit REVIEWED confirmation, it normalizes NTFS permissions and ownership only under C:\ProgramData\CreatorPulseBridge, rejects reparse points and unexpected top-level contents, and verifies the resulting ACL before starting the service. Do not instruct the owner to edit permissions folder by folder. If the helper fails, report the exact failing gate as a repository or host blocker without prescribing manual ACL surgery. If the ZIP or signer cannot be verified, stop for owner review; do not substitute an unsigned runtime. The script is owner-only, prompts once locally for task account password, starts the dedicated Sandbox task and checks loopback PING and the existing HTTPS route. It refuses an occupied port or unrelated existing task, but can recover the exact known previous Sandbox task after owner approval. Runtime/code/secret files are read-only to the service identity; only Sandbox data is writable. The new file-based launcher records a redacted startup stage, and on failure the elevated installer reports the scheduler's last result and error type/code without credentials. Before registering the task, the owner helper verifies effective batch logon with the locally entered password. It grants only SeBatchLogonRight on the exact dedicated local account SID if required, verifies effective logon again, and rolls back its new grant if that check fails. It never removes Deny rights or replaces security policy. If policy or credentials prevent batch logon, report the redacted gate; no manual policy edits or elevation by Hermes. Do not prepare a new installer for owner execution until Windows installer CI for that exact revision passes, including real scheduled-task startup and restart under a standard account. The non-elevated preflight cannot prove a protected task is absent. Do not send the owner to Event Viewer or suggest manual runas commands; use the installer's diagnostic output and report the failing gate. For this migrated host, prepare a single owner-ready action containing the reviewed helper, its exact commit, and a no-arguments invocation. Before staging, validate the actual freshly pulled file using the Windows PowerShell 5.1 Parser.ParseFile API; report parser error count and SHA256 (64 hex characters), and compare against the Git checkout. If syntax fails, stop, report the repository defect and do not give the owner a broken script to edit or execute. A folder under the agent's Windows user profile (including Documents) is agent-writable and is not an administrator-controlled staging directory. Do not claim otherwise. Open the file location or review instructions locally for the owner. Do not just report the gate as blocked; finish the preparation without invoking elevation. The owner independently reviews and stages the script in an administrator-controlled directory before executing. Do not attempt to automate the UAC approval. Never run owner code directly from an agent-writable directory; owner must review/copy it to an administrator-controlled location and verify the existing protected service code and ACLs first. No account/secret generation, Vercel changes or tunnel changes are performed by that helper.
4. If a different installation layout or existing task requires repair, prepare one consolidated owner-approved action instead of a series of commands. Use a persistent task/service with dedicated identity, restart policy and automatic startup. Confirm process identity, loopback-only binding, local authenticated PING and authenticated HTTPS PING by the owner. Agent may check public gateway health without secrets; health configured=true is not proof of storage.
5. After successful verification, owner removes or secures duplicate old private files and DB backups and reviews/revokes unnecessary owner CLI sessions (.env.local only if known to be disposable). Do not delete arbitrary existing credentials or logs. If credentials were exposed, owner evaluates rotation separately. Agent only receives its agent key, never a copy of vercel.env or bridge.env. No enrollment until isolation is verified.

## 3. Gateway and enrollment (owner boundary)
- PC09 credential provisioning: use [windows-owner-agent.ps1](windows-owner-agent.ps1), not manual file creation. An inaccessible hermes.env is UNKNOWN, not missing. The elevated owner helper reads only the existing Agent Key field from protected hermes.env/vercel.env (if both exist they must agree), or prompts privately for the existing key if absent; it never generates keys. It asks the owner to accept or decline the existing project-wide Vercel bypass, never creates a new bypass. It exports only approved agent credentials to fixed C:\ProgramData\CreatorPulseAgent-Sandbox\hermes.env and preview-bypass.secret, with Administrators/SYSTEM control and Windows USER read access. This is NOT isolation between Hermes profiles sharing USER. Do not access the original protected directory or use Vercel owner sessions. For this new helper, wait for Windows CI for the exact commit; parse locally and record hash, then open the reviewed file location for the owner to independently stage in an administrator-controlled directory and run elevated with no arguments. Do not elevate Hermes. No placeholders, manual credential file creation or search of private files by Hermes. After owner action, check only file presence/readability at the fixed output paths, never print contents; pass paths directly to bootstrap. If bypass is declined and Preview is protected, report blocked; do not try to disable protection. Before enrollment, owner must verify the old duplicate private credentials are secured and USER cannot access Bridge/operator/vault keys. The owner may retrieve the existing Operator Key privately from their password manager or protected vercel.env; never pass it to Hermes. Open the Sandbox dashboard for owner enrollment before applying MCP. Use integrations/hermes/proxy.py or the installed proxy path, not local-bridge/proxy.py.
- Keep existing Funnel routes, Vercel protection, TikTok settings and production untouched. The owner sets sandbox-only Preview variables and redeploys only if required; do not reconfigure working services. Check canonical gateway health environment=sandbox, configured=true, directPublicEnabled=false.
- Owner approves any project-wide Preview automation bypass explicitly; existing bypass may be reused only if owner authorizes it. Store only the bypass secret in a restricted file and only the agent key in the dedicated profile or agent-only file; never pass secrets in chat, URLs, Git, command-line arguments or logs. If protection blocks a terminal call, report the blocker rather than disabling protection or using owner authentication.
- Owner opens https://creatorpulse-studio-git-sandbox-total-management1.vercel.app/dashboard, connects TikTok if needed, opens AI Agent, selects account and enters Operator Key to enroll (max 3). Owner performs enrollment, not agent. Browser OAuth success is not enrollment. No real posting.

## 4. Activate MCP and validate
- Run `python integrations/hermes/bootstrap.py --environment sandbox --hermes-home <actual-dedicated-profile>` with Hermes Python. Dry-run first; if agent key is already in profile, omit --agent-env. Once isolation and owner approval are verified, add --apply and --preview-bypass-file <approved-restricted-file> if needed, optionally --agent-env <agent-only-file>. Never use default profile. Check returned connection object; exit 2 can indicate zero enrolled accounts. Do not treat install success as connectivity.
- Run installed proxy with --environment sandbox --env-file <dedicated-profile/.env> --preview-bypass-file <approved-file> --check (omit bypass flag only when not needed). Test actual Hermes CLI using `hermes -p creatorpulse-sandbox mcp test creatorpulse` if supported; inspect help first. Test list_accounts and read-only video/analytics via dedicated terminal session. Record status/count, not tokens, personal account IDs or raw records. Do not start/restart message gateways, cron, approval or posting.
- Completion requires correct environment, persistent Bridge identity, protected owner files, authenticated gateway read, at least one enrolled account, real MCP tool discovery and read-only account/video/analytics call. Distinguish partial completion and blockers.

## 5. Reporting and owner handoff
Return one report with commit, gate status (passed/blocked/not run), evidence without secrets, and any owner-only steps consolidated in one reviewed action. If owner authorization is needed, perform all independent safe work first. Never request passwords via chat or ask the owner to transcribe terminal output; have local diagnostics return a redacted summary. Resume by re-running preflight and only incomplete gates. Do not claim Windows testing from Linux CI or repository inspection.
